# v2.29.1 — Long-Story Retrieval Intelligence

## Goal
Keep Story Companion useful when a project grows from a few chapters to dozens or hundreds without sending the whole manuscript to the model or adding a heavy vector database dependency.

## Retrieval path
1. Build a `StoryRetrievalPlan` from the creator instruction and structured Story Memory.
2. Expand sparse queries using matching characters, aliases, abilities, inventory, significant events, arcs, threads, canon and revision history.
3. Convert event/arc/thread provenance into chapter-number boosts.
4. Refresh the lightweight chapter index only for new/changed/deleted Markdown files.
5. Rank indexed chapter candidates without opening every chapter.
6. Open only the strongest candidates and build short excerpts.
7. Assemble bounded context with current canon before historical chapter evidence.

## Safety / durability
`chapter-index.json` is disposable cache data, not canon. Deleting or corrupting it only causes a lazy rebuild from chapter Markdown. Story Memory remains schema v4.

## Why not embeddings yet
The current structured memory already contains strong semantic anchors: character names and aliases, abilities, items, event type/provenance, arcs and threads. Hybrid lexical + structured provenance retrieval is much cheaper and easier to audit. Embeddings remain an optional future upgrade only if real long-project tests demonstrate a recall gap.
